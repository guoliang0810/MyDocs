# LLM 在物理仿真中的角色边界

> **这不是技术偏好，是产品原则。**
> 一旦把 LLM 生成的数值放进工程决策，责任就无法归属。
> 这条边界一旦破了，后面所有 V&V、追溯链、认证努力全部归零。

---

## 一、一句话结论

> **LLM 负责编排与生成代码，数值必须由确定性代码执行。**

---

## 二、合法职责 vs 非法职责

### ✅ LLM 的合法职责

| #   | 职责          | 说明                            |
| --- | ----------- | ----------------------------- |
| 1   | **意图解析**    | 自然语言 → 结构化问题定义 / 输入卡 / API 调用 |
| 2   | **代码生成与重构** | 求解器、网格脚本、后处理脚本                |
| 3   | **编排**      | 工作流调度、工具调用、异常处理、重试策略          |
| 4   | **解释与文档**   | 把数值结果翻译成工程师可读的叙述、生成报告初稿       |
| 5   | **检索与配方**   | 从模板库 / 参数库 / 技能库中选型匹配         |

### ❌ LLM 的非法职责

| #   | 禁止行为                                    | 为什么                        |
| --- | --------------------------------------- | -------------------------- |
| 1   | **直接输出任何将进入工程决策的数值**（应力、应变、温度、寿命、重量、频率） | 无法追溯、无法复现、无法验证             |
| 2   | **直接给出 GCI、误差带、置信区间**                   | 这些是求解过程的产物，不是语言模型的产物       |
| 3   | **在没有可执行求解器的情况下“估算”结果**                 | 估算值会被下游当作计算值使用             |
| 4   | **替代 CAE 求解器做有限元/流体求解**                 | 违反 [[仿真可信度V-V与标准体系]] 的全部前提 |

## 三、为什么 LLM 不能算数——有来源的论证

### 论证 1：算术缺陷是结构性的，不是模型规模问题

依据 **`2608.13129`**（*Numeracy in Large Language Models*）：

LLM "在基本数值任务上仍不可靠，包括**量级比较、大整数算术、分数、科学计数法**"。

**根因**：tokenization 不保留数位语义——
"87439" 可能被切成 "874"+"39" 或 "87"+"439"，模型**无法稳定感知位值**。
论文提出 Numerical Grounding Framework，分解为：
- **Representational Grounding**（表示层接地）
- **Procedural Grounding**（过程层接地）

**实证**：证券时报实测 12 个大模型，**8 个在"9.11 和 9.9 哪个大"上答错**。

> ⭐ 关键论断：**"语言模型是文科生而不是理科生"**——
> 学会的是相关性，数学推理需要的是因果性。

### 论证 2：LLM 在 CAE 中的正确定位就是"生成代码"

依据 **`2509.11447`**（LLM-empowered CAE）：
LLM 自动化的是 "**derivation, code restructuring, implementation**"（推导、代码重构、实现），
把降阶方法从"人工推导 + 手工改代码"变成"自然语言描述 PDE → 生成求解器实现"。

> **数值本身由生成的求解器算。**

依据 **`2509.25194`**（LLM-PDEveloper）：
LLM-PDEveloper 明确"由数学与算法描述**直接翻译为源代码**"，
并诚实报告 "achieving **moderate success rates**"，且**专门分析 LLM 语法错误并提出修复方案**。

### 论证 3：CAD-Recode 的"生成—执行—验证—选优"闭环

依据 **`2412.14042`**：
LLM 生成 CadQuery 代码 → **执行** → 用 Chamfer Distance **验证** → 10 个候选中选优。

> ⭐ **LLM 从不直接输出几何，它输出代码，几何由内核算。**

## 四、⭐ 强制机制：数值溯源标注

> **LLM 输出的一切数值必须标注来源。无来源的数值一律视为无效。**

推荐格式：

```
computed_by: <solver>@<version>
input_deck_hash: <sha256>
mesh_id: <id>
convergence_gci: <value>
```

这条机制同时实现三个目标：
1. **技术可信** —— 数值可复现
2. **审计合规** —— 满足 [[仿真可信度V-V与标准体系]] 的追溯要求
3. **工程责任** —— 数值有明确的归属主体

## 五、⚠️ 术语纠错：这几个名字容易搞混

| 名称 | 真实身份 | 常见误解 |
|---|---|---|
| **ChatCAD** | ⚠️ **不是论文**，是创新奇智的产品（奇智孔明工业大模型，2024-03-27 首发 0.1 版）。检索到的同名 GitHub 项目与它无关 | 被当成 arXiv 论文引用 |
| **MOD-UQ** | LLNL 的多物理场模块化 UQ 框架 | 与神经算子场景的 UQ 库混用 |
| **NeuralUQ** | 神经算子/PINN 场景的 UQ 框架（`2208.11866`） | 同上 |
| **DeepONet 许可** | 已由 Apache-2.0 改为 **CC BY-NC-SA 4.0** | 以为仍是 Apache，商业分发有风险 |

## 六、落地检查清单

在设计任何 AI 仿真功能时，逐条确认：

- [ ] 产品中**没有任何路径**让 LLM 直接返回进入决策链的数值
- [ ] 所有数值都有 `computed_by` 溯源字段
- [ ] 求解器调用失败时，LLM 只能报告失败，**不能给出估计值**
- [ ] 代码生成走"生成—执行—验证—选优"闭环（参考 CAD-Recode）
- [ ] 对 LLM 生成代码做**语法与语义双重校验**（参考 LLM-PDEveloper 的做法）
- [ ] 产品文档中如实披露 LLM 的成功率区间（参考 "moderate success rates" 的诚实表述）
- [ ] 客户数据不进入 LLM 上下文，也不用于训练（除非单独书面授权）
